# Layout H 独立车辆道路推演

看板默认显示车辆专用路网，飞机滑行道作为可选参照层。车辆寻路只使用车辆图；在平面交叉处，两张图也不共享节点或边。保留最新论文包 Layout H 的 30 个飞机机位位置。

## 配置依据

Layout H 原始数据只提供飞机节点与中心线，没有航站楼、建筑、机翼包络、道路宽度或正式的车辆交通规则。本版本据此推演一套可用于平台仿真的车辆道路，假设北侧及两侧具有可用服务空间；不是实测机场道路设计。

- 外围环路在原飞机网络之外，左右边界 x=±145 m，南北边界 y=-40/245 m，连接各基地，承担跨区行驶。北侧横路连接各内侧服务分区。
- 西、东内侧服务路沿 x=±78 m 布设，从北侧接入，沿机位群纵向运行；中央服务路在 x=±8 m 间错位，绕开两个朝内机位的停靠点。内侧服务路南端不再接入南环路，减少跨越南部滑行通道的次数。
- 每个机位设一个独立车辆服务点 SP_01–SP_30。沿“飞机连接点→机位”的方向再外移 6 m，表示机位背向滑行道的一侧。车辆支路连接服务点与所属分区道路；相邻斜列机位附近采用折线绕接。
- 行李基地分东西两个停车湾，另设配餐、摆渡、巡检充电基地和北区巡检点。车辆在基地支路上待命，不占据机位或主路节点。

6 m 偏移及所有坐标沿用原始示意图的米制尺度，仅用于区分停靠点和道路；未校核机翼净空、转弯半径、尾流、建筑避让和车道宽度。图中的线表示道路中心线，双向通行目前仍采用单线抽象。

## 道路与通行规则

| 层级 | 作用 | 仿真速度上限 |
|---|---|---|
| 外围环路 | 基地接入、跨区运输 | 20 km/h |
| 分区服务路 | 沿机位群分配车辆 | 12 km/h |
| 作业支路 | 进入服务点、基地和巡检点 | 5 km/h |

当前配置为 98 个车辆节点、98 条双向路段，包含 30 个机位服务点、5 个基地、1 个巡检点及 11 个滑行道交叉点。

11 处交叉均与飞机滑行道中心线相交，未穿过机位接入支线。程序在交叉处切分车辆边并生成 X_01–X_11；仿真到达交叉节点后停车 3 秒再继续。这是演示等待，尚无飞机占用检测、停止线前等待、真实许可或路口冲突区预约；不能理解为已经实现空地协同放行。

寻路按道路长度执行 Dijkstra；限速在运动推进时生效，不参与最短距离优化。保留原有跟车、转弯减速和对头让行逻辑，不包含车道级会车和完整路口互斥。固定时长停车不作为拥堵成本，尚未接入 MAPPO。

## 典型路线

- 西区行李基地 → 西侧外围道路 → 机位 01 服务点：约 166 m，无滑行道交叉。
- 配餐基地 → 东侧外围道路 → 北侧横路 → 东区服务路 → 机位 20 服务点：约 598 m，经过 2 个交叉等待点。
- 东区行李基地 → 外围环路 → 北侧横路 → 西区服务路 → 机位 07 服务点：约 709 m，经过 2 个交叉等待点。

以上是任务起点到终点的道路距离。车辆任务生命周期为：当前位置前往起点 → 前往终点 → 在终点服务 → 返回本车基地。默认任务在无随机异常的仿真中均可完成并返回。

看板的“查看起终点行车路线”可选择基地、机位服务点和巡检点，显示路线长度及交叉数量。“叠加飞机滑行道参照”用于观察交叉位置，不会改变车辆寻路。

## 维护方式

- `data/aircraft_layout_h.yaml`：保存上次同步的最新 Layout H 飞机网络及原始代码 SHA256。仅参照，不加入车辆邻接表。
- `scripts/build_vehicle_layout.py`：维护分区走向、服务点偏移、基地位置与限速，自动计算道路交点和滑行道交叉点。
- `data/apron_layout.yaml`：生成后的默认车辆图，包含参照文件 SHA256。
- `data/vehicles_seed.yaml` / `data/tasks_seed.yaml`：车辆基地和任务端点，使用 SP_*、DEPOT_*、CHECK_*。

修改生成脚本后执行：

```bash
python scripts/build_vehicle_layout.py
pytest tests -q
```

生成脚本使用仓库中的 Layout H 快照，不会自动从算法仓库拉取新版。更新参照快照时须重新生成并核对道路与新增机位、滑行道的交叉。更换路网后重启 API，使用新的 `APRONOPS_DB_PATH` 隔离旧拓扑的演示记录；看板布局缓存最多保留 10 秒。

车辆路网迁移时使用的 `apronops-vehicle-h-v1.db` 已保留。运行闭环版本默认使用 `apronops-operations-v1.db` 并支持现场恢复，详见 [运行与异常处置](operations.md)。数据库均不提交 Git。

Docker Compose 将持久化卷挂载到 `/app/runtime` 存数据库，配置文件从镜像的 `/app/data` 读取。更新代码后执行 `docker compose up --build -d`，不会再被卷中遗留的旧 YAML 遮盖。同名卷中的原数据库仍保留。
