# 基地泊位、排队预测与滚动优化

本阶段只扩展平台规则仿真、运行恢复和调度优化。在线 API 与无界面实验使用同一推进逻辑，不接入学习模型、训练代码或研究仓库。

## 基地资源与进出站

`data/depots.yaml` 为五个基地配置泊位数 `capacity`、取货/进站办理时间 `pickup_s`、持续阻塞检查阈值 `recovery_after_s`。默认每基地 2 个泊位，巡检办理 5 秒、行李/摆渡 10 秒、配餐 15 秒；这些是合成场景参数。

每辆停在基地的车辆占用一个泊位，包括空闲、故障和作业车辆。泊位上的车不作为道路前车障碍。车辆到达进站支路起点后申请泊位：按申请先后 FIFO 排队，有空位时先预留，再驶入支路；到达基地时将预留转为占用。占用＋预留不能超过容量，也不能分配同一泊位给两辆车。驶离泊位开始产生实际位移时才释放原泊位。

满位车辆在支路入口的逻辑等候区排队，等候区中的静止车辆不挡住出站车辆。基地泊位与等候区都采用图节点坐标表达，没有独立的泊位几何、转弯轨迹或有限等候区长度。它们是道路之外的容量抽象，地图上同坐标不代表实体车辆重叠，也不能用于校验真实车道安全距离。

取货办理在泊位内计时，办理完成后才把任务从 ASSIGNED 改为 IN_PROGRESS。定位故障暂停办理并保留剩余时间；取货前通信故障仍按现有规则重新排队任务。已驶入支路的故障车辆保留预留泊位，避免其他车辆被放入同一个泊位。

实验 YAML 可以用 `depots` 覆盖基地设置：

```yaml
depots:
  DEPOT_AMR:
    capacity: 1
    pickup_s: 15
    recovery_after_s: 30
```

配置必须引用已有 depot 节点，容量为正整数，办理时间和恢复阈值为正有限数。初始驻车数超过配置容量时拒绝启动，不能默默丢弃车辆。其余机位服务点和检查点目前仍遵守原有节点阻挡规则，没有扩展为多泊位站点。

## 排队预测

`deadline_forecast` 与 `rolling_optimization` 共用预计完成时间计算：公开飞机穿越预测＋道路限速行驶时间＋基地排队＋取货办理＋任务服务时长。飞机实际占用、车辆故障与封路仍由共同执行核心约束，预测不能授予通行权。

预测器把每个泊位视为一个服务器，读取当前占用、预留与已到入口的队列，估计车辆到达时的剩余等待。正在办理或服务中的车辆使用剩余时间；进站预留包含剩余支路行驶时间。故障恢复时间、空闲车辆未来何时出站不从场景脚本中偷读，这类泊位释放未知，接口返回 `null`。

用于调度比较时，未知等待采用明确的 120 秒启发式惩罚。它不是承诺的恢复时间，也不是等待上界。排队估计尚未完整模拟加减速、沿路排队或远处所有尚未排队车辆的到站竞争；滚动策略另外加入本轮同时派往同基地的办理压力项。

## 持续阻塞与死锁恢复

系统分别记录持续阻塞与确认的资源循环等待：入口车辆指向占用/预留所需泊位的车辆以及队列前车，形成等待依赖图；强连通分量包含多辆互相依赖车辆时，记录 `deadlock_cycle_detected`。普通有确定服务结束时间的队列不按死锁处理。

满位且泊位释放时间未知，或者车辆长时间被前车挡住，会在阈值后记录持续阻塞事件。可执行的恢复动作包括：

- 将满位基地内可移动车辆驶往没有排队且有空泊位的基地，先预留逃逸泊位。优先空闲车辆，其次允许尚未离开泊位且等待其他基地资源的车辆。正在办理、服务或故障的车辆不会被自动搬走。
- 原任务、货物阶段和所属基地保持不变。带任务车辆到达临时基地后继续原目标；空闲车辆留在临时泊位等待后续任务，所属基地仍用于任务结束后的返程。
- 车辆因前车阻挡且尚未进入路段时，尝试避开该边重新寻路；已经驶入路段时不会跳回节点、强制掉头或穿过故障车。

挪车使用同一物理运动、封路与空地互锁约束，有开始、到达和阻塞解除事件。执行中发生故障可以暂停并在修复后继续。若没有可用空位、道路不通，或无法在当前位置安全改道，记录 `deadlock_unresolved` 并保留现场，等待封路/故障修复或后续状态变化后再尝试。

这是一组有限恢复规则，不保证解决任意路网死锁。全部基地已满且没有逃逸泊位、路段内部相向阻塞等情况仍可能需要人工处置。`detected` 统计持续阻塞事件，`cycles` 单独统计资源循环，不能把前者全部当作已证明的死锁。

## 滚动联合调度

`rolling_optimization` 每 15 秒仿真时间重新求解一次联合任务—车辆分配。每次只提交当前可执行的分配，然后观察执行后的真实状态，再进行下一轮。它不改变已分配、已取货或正在服务的任务归属。

当前有界求解器无需新增依赖：

1. 从已释放、前置任务完成的任务中选择最多 6 项。按每 300 秒等待分档优先照顾老任务，再按截止时间、优先级和 ID 排序；取最多 5 辆兼容空闲车辆。
2. 枚举不重复的任务—车辆匹配，每轮最多访问 20,000 个搜索节点。先最大化可分配数量，再最小化优先级加权延误与 `0.01 × 预计完成耗时`，并计入未分配任务的下一轮等待惩罚和同基地办理压力。
3. 只提交当前一轮匹配。每辆车和任务最多出现一次；不兼容、无路径和前置依赖未满足的组合不会执行。

在搜索未截断时，求得的是该候选集合、该估计目标下的最优匹配；不是整个航班计划的全局最优，也不是连续轨迹优化。事件中记录候选数、搜索节点、目标值、分配、周期和截断标记。计算耗时仍保存在独立 `performance.json` 中，不污染确定性结果。

回归测试使用一个明确的反例：贪心选择使两任务预计成本为 1＋100，而联合匹配选择 2＋2。该测试验证求解器确实联合比较组合；实际机场合成场景的优劣仍以完成率、延误和等待日志为准。

## 看板与接口

运行总览的“调度策略”可切换三种规则，提交后写入运行快照。切换只影响后续调度/节点寻路，原有任务继续。`GET /dispatch/policies` 列出策略，`POST /dispatch/policy?policy=rolling_optimization` 切换策略。

`GET /state` 新增 `depots`、`recovery`、`wait_for`、`deadlock_cycles`、`policy`、`dispatch`，车辆新增 `recovery_action`。看板和实验回放均展示泊位占用、预留、排队长度、等待估计以及恢复统计；车辆表展示正在执行的挪车动作。办理过程仍属于任务的取货前阶段。

快照版本为 4，保存泊位/预留、FIFO 顺序、办理剩余时间、阻塞计时、恢复绕行目标与下一次滚动调度时刻，版本 1/2/3 可读取。旧快照没有容量，迁移时按默认值、实际驻车数及已驶入进站支路的车辆数推定容量，为这些在途车辆补预留，并保留全部原有车辆。已有版本 4 现场恢复使用快照内的基地配置，修改 YAML 不会覆盖正在运行的泊位分配；新配置应使用新数据库或新实验。

## 实验与复核

```bash
python -m apronops.experiments.run \
  --scenario configs/experiments/depot_pressure.yaml \
  --seeds 1 2 3 \
  --policies priority_distance deadline_forecast rolling_optimization \
  --output results/experiments/depot-pressure-001
```

新增 `depot_pressure.yaml` 提供单泊位巡检基地、故障驻车和分时释放的两项任务；也应继续运行原有 routing、turnaround 场景。场景约束对三种策略一致，输入哈希包含基地配置，旧结果不能直接混入本版本比较。

新增指标包括累计基地排队车辆秒、持续阻塞检测/解除/未解除数、资源循环次数、挪车/改道次数、滚动求解轮数、泊位容量违规子步数。回放每帧包含独立的资源表和恢复状态。运行截止时仍存在的队列、未完成任务和未解除阻塞均保留，不按成功清空。

验收覆盖容量唯一性、FIFO、满位恢复、真实位置连续性、故障不擅自解除、关闭逃逸路线、泊位互锁循环、办理暂停续跑、恢复中重启、联合匹配反例、策略切换持久化及离线回放。

本版本工程验收：routing、turnaround、depot_pressure 各运行种子 1/2/3 和三种策略，共 27 次；完成数分别为 3/3、4/6、2/2，所有运行的泊位容量与图冲突区违规子步计数均为 0。单泊位场景每次累计排队 241 车辆秒，发起 1 次挪车并解除 1 次持续阻塞，最终未解除数为 0。该场景没有随机扰动，三个种子用于验证运行协议，不能当作独立统计样本。

turnaround 的观测终点仍有未完成保障任务；种子 1 下滚动规则的延误下界约 1013 秒，最近距离规则约 981 秒。现有样本没有证明滚动规则全面更优，保留这些结果作为后续调参和更丰富场景测试的依据。
