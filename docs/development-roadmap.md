# 平台分阶段开发路线

本轮从可演示的车辆平台开始，逐步建立可复现的研究环境。每阶段单独验证与提交，避免把“已有界面”与“已经具备运行能力”混淆。

## 第一阶段：异常处置与运行连续性（已实现，2026-10-28）

已实现故障恢复、未取货任务转派、道路封闭与重开、现场快照、实时看板和指标修正。完整规则与接口见 [运行与异常处置](operations.md)。

验收覆盖：

- 未取货任务转派给兼容车辆，最终只完成一次；原车修复后返回自己的基地。
- 在途已取货任务以及作业剩余时长保留；恢复不重置车辆坐标。
- 同车多个故障全部解决后才恢复；重复处置不覆盖第一次处置记录。
- 封闭路段不参与最短路；无路可走时等待，恢复后继续；已驶入封闭边的车辆不跳回节点。
- API 成功响应前提交运行快照；提交失败时回滚内存；旧数据库和不同拓扑不会被静默覆盖。
- 同一数据库连续启动恢复相同状态；地图、任务、等待原因与封路状态按同一快照刷新。
- 到期未完成任务进入准时率分母，告警解决率与人工干预率区分。

本阶段仍使用规则调度。物理货物交接、车道级会车、路口互斥、车辆充电和真实数据接入尚未实现。

## 第二阶段：航班驱动的任务与飞机穿越约束（已实现，2026-10-30）

新增 Flight 和 CrossingOccupancy；Task 增加航班、释放时间、前置依赖及服务时长。合成航班模板生成行李、配餐和保障后检查任务，支持延误更新和版本冲突保护。

飞机输入区分预测窗口与申请时段。图冲突区空闲后授予实际占用，区内车辆先清空；车辆在区外等待并与飞机互斥。申请可因区内故障车而推迟，这是仿真互锁，不代表真实航空器占用遥测或机场放行系统。

完成快照 v1→v2 兼容读取、航班与穿越页面、演示场景及测试。验证了依赖门控、幂等更新、延误不重置作业、占用期间区外停车、请求窗口不被大步长跳过和重启恢复。详细规则与未覆盖范围见 [航班与穿越](flights-and-crossings.md)。

## 第三阶段：独立实验核心与规则基线（已实现，2026-10-30）

在线与离线共用无数据库的推进核心，提供 `reset/step` 和批量 CLI。固定时钟、独立随机源、确定事件 ID、配对输入哈希和代码/依赖版本，保存任务、事件、采样帧和指标；墙钟性能单独统计。

已实现最近车辆＋最短距离、截止时间优先＋公开预测等待路径两种规则。看板可加载本机结果或上传 JSON，按时间轴查看车辆、任务、封路与飞机管制，不推进现场。相同输入重复运行、部分结果标记、未完成任务统计和回放一致性均有测试。

两份合成场景、三个种子、两种策略共 12 次运行的工程验收已完成。预测规则在基地入口遇到停驻车辆时表现更差，相关阻挡原因和指标被保留。使用方式、指标口径与限制见 [实验与回放](experiments.md)。

原计划的小规模滚动优化尚未实现，移入下一阶段，与基地容量和排队预测一起处理，不计入本阶段已完成能力。

## 第四阶段：优化与 MARL 实验（待开发）

先补充基地泊位、站点容量、死锁恢复与小规模滚动优化基线，再围绕“航空器通行约束下保障车辆调度”建立明确的状态、动作、奖励和硬约束，在研究仓库中训练与评估，通过版本化接口与平台互通。

先通过文献比较确认方法贡献，再设计预测误差、需求强度、车队规模及封路扰动实验。训练/验证/测试分离，使用独立种子和置信区间；消融占用预测、动态绕行及规划先验。最终论文结果必须来自可追溯日志。

不把现有飞机模型权重直接作为车辆策略，不把演示看板或推演道路本身当作算法创新证据。
