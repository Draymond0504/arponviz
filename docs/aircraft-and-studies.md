# 航空器运行与空地协同对照实验

平台现在包含真正移动的航空器：在 Layout H 航空器路网上从入口 `900` 滑行到航班机位，等待保障完成与车辆撤离，再滑行到出口 `901`。车辆继续使用独立车辆道路。所有运动、任务及互锁都由同一仿真时钟推进，独立于研究和训练代码。

## 直接看飞机运行

在看板“实验回放”选择 `aircraft-turnaround-001/aircraft_turnaround-rolling_optimization-seed1/replay.json`，点击播放。在“追踪”下拉框选择“航空器 AC_001”，紫色飞机图标、路线与引线标签用于观察滑行。右栏显示航空器、保障任务、基地和管制状态；“跳至”包含进场、到位、离位与离场等关键帧。

这个本机示例包含 1 个航班、3 项航班保障和 1 项北区巡检。仿真从 `2026-01-01T00:00:00Z` 开始，事件记录为：

| 相对时间 | 运行事件 |
|---|---|
| 00:10 | AC_001 开始进场滑行 |
| 00:44–00:48.5 | 实际通过 X_02，清空后释放空地交叉区 |
| 01:02.5 | 实际到达 SP_07 对应的飞机机位 |
| 约 29:40 | 全部 4 项任务完成，飞机继续等待计划离位 |
| 45:05.5 | 开始离位滑行 |
| 45:16–45:20.5 | 通过 X_05 |
| 46:18 | 到达出口，航空器离场 |

精确时刻来自事件文件；动画每 2 秒采样，例如实际 00:10 开始的动作在 00:12 的下一采样帧出现。飞机早到时，保障仍等待计划任务释放时间；晚到时，即使计划释放时间已经到达，保障也必须等待实际到位。

在新机器上生成示例：

```bash
python -m apronops.experiments.run \
  --scenario configs/experiments/aircraft_turnaround.yaml \
  --seeds 1 --policies rolling_optimization \
  --output results/experiments/aircraft-turnaround-002
python -m apronops.dashboard.replay_player \
  results/experiments/aircraft-turnaround-002/aircraft_turnaround-rolling_optimization-seed1/replay.json \
  --output results/experiments/aircraft-turnaround-002/aircraft-animation.html
```

生成的 HTML 可直接离线打开；动画数据不会写入在线现场。

## 在线操作

“航班与穿越”新增“载入航空器协同演示”，显式点击后创建 1 架飞机、1 个航班和 3 项保障任务。10 秒仿真时间后进场，机位为 SP_07。重复点击不重复创建；原有“载入航班与穿越演示”仍是固定请求窗口演示。

也可以先创建一个尚未开始保障的航班，再展开“为航班添加航空器运行”，填写飞机 ID、关联航班和进场偏移时间，点击“加入航空器仿真”。已开始保障的航班不能事后附加飞机。一架飞机对应一个航班；关联飞机后禁止直接更换机位，避免改变在途目的地。航班延误更新仍支持时间窗修订，不会重置飞机物理位置或悄悄重排已录入的进场时间。

运行总览显示飞机与车辆；“航班与穿越”的航空器表显示进场/停驻/离位/离场状态、等待原因和实际到离位时间。

| 接口 | 内容 |
|---|---|
| `GET /aircraft` | 所有航空器的状态、位置、航班关联、当前路段、里程、等待和实际时间 |
| `POST /aircraft` | 添加飞机，字段为 `id`、`flight_id`、`taxi_start_offset_s`；入口默认 900，出口默认 901，速度默认 4 m/s，示意机长默认 12 m |
| `POST /scenarios/aircraft-demo` | 显式载入航空器协同演示，重复安全 |
| `GET /state` | 新增 `aircraft`；未实际到位的关联任务显示等待原因 |
| `GET /flights` | 新增飞机 ID 和实际到位/离位时间 |

## 互锁与当前模型边界

飞机位置沿航空器图的路段连续推进。空地交叉区在航空器路径上对应一个带机长余量的区间：飞机到区间入口时提出实际通行申请；区内车辆先清空，飞机获得占用权后进入，尾部余量通过出口后才释放。`aircraft_motion` 类型请求的预计结束时间不会直接取消占用权，重启也不会把仍在区内的飞机放行状态丢掉。手动录入的合成窗口继续使用原来的持续时长语义。

首次迭代采用**整个航空器滑行网络单架放行**：最多一架飞机滑行，其他飞机在外部入口或机位等待。机位在进场开始时被保留，直至对应飞机离场后释放；同一机位不会被两架飞机同时占用。飞机离位还需满足计划离位已到、全部关联任务完成、机位服务点 12 米内没有车辆。这个规则偏保守，旨在先验证时序与互锁，不代表机场吞吐能力。

实际到位是保障任务调度的附加门控。车辆完成作业后物理撤离，飞机才能离位；没有让保障提前开始来美化结果，也没有把未离位的飞机当作准点离场。

当前不模拟空中航迹、跑道起降、独立推回车作业、复杂滑行管制、多机同时滑行、转弯翼尖包络、机型性能或真实尺寸的碰撞检测。速度和机长是示意参数。图标大小不是实际机身几何，零冲突仅对应现有图交叉区模型。

运行快照升级为版本 5，保存飞机状态、路段进度、滑行占用、实际时间和航空器参考图指纹；仍读取版本 1–4。升级已有现场时没有自动新增飞机或任务。已有飞机的快照若对应不同航空器图会拒绝恢复。

## 多条件对照实验

配置：[air_ground.yaml](../configs/studies/air_ground.yaml)。使用五个条件，每次只改变一个配置因素：

| 条件 | 航班数 | 车辆数 | 每基地泊位 | 故障次数 |
|---|---:|---:|---:|---:|
| 基准 | 1 | 5 | 2 | 1 |
| 需求增加 | 3 | 5 | 2 | 1 |
| 车队扩大 | 1 | 10 | 2 | 1 |
| 容量收紧 | 1 | 5 | 1 | 1 |
| 故障增加 | 1 | 5 | 2 | 3 |

每个条件跑种子 1/2/3 和三种策略，共 45 次，每次观测 4800 秒。每个航班生成 3 项任务。种子实际改变进场时刻、故障起点与时长；独立随机流使条件间共有航班和共有故障保持相同前缀。同一条件、同一种子的三种策略必须具有相同输入哈希。

```bash
python -m apronops.experiments.study \
  --config configs/studies/air_ground.yaml \
  --output results/experiments/air-ground-study-003
```

本机 `001` 保留首次发现问题的结果，`002` 是修复候选车辆筛选后的验收批次，所以复跑示例使用新目录 `003`。输出目录必须不存在。只需实验依赖，不需要数据库、API 或 GPU。

原来的实验 YAML 新增可选 `aircraft` 和 `vehicles`：前者关联同场景航班及进场时间，后者可替换完整初始车队；默认省略时沿用既有行为。扩大车队时必须同时保证配置泊位容得下初始驻车数。研究批次导出的每个冻结场景可以直接交给原来的 `experiments.run --scenario` 重跑。

## 看板分析与统计口径

新增“实验对比”页面，选择 `air-ground-study-002`。可比较完成率、到期准时率、未完成任务、任务延误下界、飞机离场数量、离位延误下界、道路等待、基地排队、未解除阻塞、总里程和空驶里程。

“策略原始值”展示各条件的种子均值与样本标准差；“相对最近车辆策略的配对差值”先对同一种子相减，再汇总均值与标准差。差值不是两个无关均值的比较。只有所有选定策略都成功运行、输入哈希一致的种子组才进入两种统计；失败、中断、缺少策略或哈希不一致的组会显示为未纳入，而不是静默按零处理。

只有 3 个种子，误差线是描述性标准差，不是置信区间，也不足以宣称算法普遍更优。原始运行表保留每次的任务总量、完成数量和飞机数量；可下载 CSV 或单次回放，切换到“实验回放”完整播放。

新增航空器指标：

- `aircraft_total / aircraft_arrived / aircraft_departed`：已加入世界的飞机总数、已实际到位数、已到出口离场数。
- `aircraft_distance_m`：沿滑行图的累计实际行驶米数。
- `aircraft_wait_s`：含机位保障、放行、空地交叉及撤离等待，不包含单纯等待计划进场/离位时间。
- `aircraft_departure_delay_lower_bound_s`：相对计划离位的累计延误；尚未离位时用停止时刻计算下界。它不是到达出口的离场延误。

“运行 completed”表示到达观测终点，不意味着全部飞机已经离场。故障暂停可能降低统计到的道路等待，不能只看等待指标就宣称故障改善了运行。

## 已验证结果（2026-10-30）

修复后的 `air-ground-study-002` 共 45/45 次运行完成，全部输入配对通过，所有任务最终完成、所有飞机最终离场，泊位与交叉区违规子步合计为 0。

| 条件 / 指标 | 最近车辆 | 截止时间预测 | 滚动优化 |
|---|---:|---:|---:|
| 基准，到期任务准时率均值 | 100% | 100% | 100% |
| 3 航班，到期任务准时率均值 | 77.8% | 77.8% | 77.8% |
| 3 航班，任务延误下界均值（秒） | 830.0 | 830.0 | 884.8 |
| 3 航班，飞机离位延误下界均值（秒） | 586.4 | 586.4 | 617.1 |
| 5 辆车，路径等待均值（车辆秒） | 607.5 | 607.5 | 607.5 |
| 10 辆车，路径等待均值（车辆秒） | 413.8 | 413.8 | 413.0 |
| 单泊位，路径等待均值（车辆秒） | 694.7 | 694.7 | 695.5 |

这次实验说明：在这组配置下，增加航班会把保障排队传导为飞机离位延误；增车和收紧泊位会改变道路等待；滚动策略在高需求条件下并没有优于另外两种策略。它是初步敏感性验证，不是容量极限或泛化结论。

首次运行还发现：原滚动策略按车辆 ID 截取前 5 辆，扩大车队后可能没有任何牵引车进入候选，行李任务永久等待。现在先按候选任务类型保留兼容且可达车辆，再补充低预计成本车辆，仍最多 5 辆参与联合搜索。原始 `001` 记录保留，回归测试覆盖该问题。
