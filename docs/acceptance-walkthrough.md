# 完整测试案例：一次机坪保障班次

本案例介绍当前平台的全部主要能力，并给出可复现的输入、操作步骤和验收标准。范围为 ApronOps 的规则仿真、调度、运营看板和实验工具，不涉及 MARL。

本文的六任务班次使用合成飞机穿越窗口。新增的完整航空器滑行、实际到离位门控和多条件实验见 [航空器运行与空地协同对照实验](aircraft-and-studies.md)，可继续播放带移动飞机的新案例。

建议先用离线回放看完整业务过程，再在独立在线现场体验表单，最后运行边界测试。离线场景与在线表单使用相同的运行核心，但它们不是同一份现场：**选择回放不会把实验数据导入在线数据库**。

## 1. 当前能做什么

| 能力 | 当前行为 | 查看位置 |
|---|---|---|
| 机坪地图与车辆道路 | 基于 Layout H 推演的独立车辆路网：98 个车辆节点、98 条双向路段、30 个机位服务点、5 个基地；可叠加飞机滑行道参照 | 运行总览、实验回放 |
| 路线与运动 | 起终点寻路、封路避让、20/12/5 km/h 分级限速、加减速、转弯减速、跟车与相向让行；轨迹高亮最多 3 辆车 | 运行总览的路线预览、地图和车辆表 |
| 任务闭环 | 创建行李牵引、配餐、巡检任务；按车型兼容性分配，驶往起点、办理、前往终点、服务、完成、返回所属基地 | 运行总览、异常处置的事件表 |
| 基地容量 | 泊位占用、进站预留、FIFO 入口排队、办理倒计时；停驻及入口等候车辆不作为道路障碍 | 基地泊位与入口排队、泊位与排队明细 |
| 排队预测 | 结合占用、预留、队列和剩余办理时间估计等待；不知道泊位何时释放时显示空值 | 基地表的预计等待、预测调度策略 |
| 阻塞与恢复 | 检测持续阻塞及基地资源循环等待；可移动车辆驶往有空位的备用基地，或在节点尝试改道；无法恢复时保留原因 | 车辆等待原因、恢复动作、恢复统计、事件 |
| 三种调度策略 | 优先级与最近车辆；截止时间与排队预测；每 15 秒滚动联合匹配 | 运行总览 → 调度策略 |
| 航班保障 | 一次录入生成行李、配餐、保障后检查；检查等待前两项完成；支持延误更新和版本冲突检查 | 航班与穿越 |
| 空地互锁 | 11 个交叉区；区分预测、申请与实际授予；申请后禁止新车进入，区内车辆清空后授予飞机完整占用时长 | 航班与穿越、地图、回放 |
| 故障与处置 | 注入通信/定位故障；未取货通信故障可转派，已取货或服务中的任务保留；所有故障解决后续跑 | 异常处置 |
| 道路管制 | 双向封路、节点绕路、路段中停车、不可达等待；解除关联告警同步恢复道路 | 异常处置、运行总览 |
| 运营复盘 | 任务完成率、到期任务准时率、告警解决率、逾期未完成；事件、车辆与轨迹查询 | 运营复盘、API |
| 重启与异常写入保护 | 保存路段进度、任务阶段、服务剩余时长、队列预留和恢复动作；重启续跑；写入失败回滚，后台失败则暂停并报告 | 状态版本、`/health`、SQLite 快照 |
| 批量实验 | YAML 场景、固定种子、三策略共用输入、源码及输入哈希、事件/任务/指标导出、保留失败和中断结果 | 命令行、实验结果目录 |
| 离线回放 | 选择本机结果或上传 `replay.json`，逐帧查看地图、任务、泊位、封路及穿越状态 | 实验回放，不依赖现场 API |

电量不足、心跳超时、定位连续劣化的检测规则也已实现；电量告警不等同于已实现充电站、充电排程或换电流程。接口清单见 [运行与异常处置](operations.md)、[航班与穿越](flights-and-crossings.md)、[基地与优化](depots-and-optimization.md)。

## 2. 准备与运行

在平台仓库根目录操作。已有 `.venv` 可直接激活；新机器推荐 Python 3.11/3.12：

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

如果云服务器只跑实验，安装 `requirements-experiments.txt` 即可，不需要 API、数据库或 GPU。

运行这个 80 分钟仿真班次：

```bash
python -m apronops.experiments.run \
  --scenario configs/experiments/acceptance_shift.yaml \
  --seeds 1 \
  --policies priority_distance deadline_forecast rolling_optimization \
  --output results/experiments/acceptance-shift-002
```

80 分钟是仿真时间，命令不按真实时间等待 80 分钟。每次必须使用新目录；本次已验证的结果保存在本机 `results/experiments/acceptance-shift-001`，重跑示例使用 `002`。结果目录被 Git 忽略，在其他机器上需要执行命令生成或自行复制。

这个实验不读写在线 SQLite，也不会清空正在使用的看板现场。实验初始车辆取自车辆种子，任务为下文的 6 项；新建在线数据库另有 4 项演示种子任务，不能把两者的计数混用。

## 5. 本次实测结果与通过标准

2026-10-30，在平台实现提交 `5980bf7` 加入本案例配置后运行种子 1；三次输入哈希一致，三次均到达 4800 秒。对应本机 `acceptance-shift-001/comparison.csv`：

| 未完成任务 / 累计延误下界 | 0 / 0 秒 | 0 / 0 秒 | 0 / 0 秒 |
| 基地排队（车辆秒） | 272 | 272 | 272 |

| 其中交叉等待（车辆秒） | 89 | 89 | 79 |
| 其中前车等待（车辆秒） | 449 | 449 | 446 |
| 持续阻塞检测 / 解除 / 未解除 | 3 / 3 / 0 | 3 / 3 / 0 | 3 / 3 / 0 |
| 挪车 / 节点改道 | 2 / 0 | 2 / 0 | 2 / 0 |
| 基地循环死锁 | 0 | 0 | 0 |
| 泊位容量违规 / 交叉区违规子步 | 0 / 0 | 0 / 0 | 0 / 0 |
| 到申请时刻仍未授予的飞机请求 | 0 | 0 | 0 |
| 滚动求解轮数 | 0 | 0 | 5 |

所有策略总里程约 7677.63 米，空驶约 5304.82 米。等待按车辆累计，两辆同时等 10 秒算 20 车辆秒；不要解释成班次被延长了相同秒数。滚动求解轮数记录有候选任务/车辆的实际求解，不能用 `4800 / 15` 推算。

本案例通过条件是：完成全部 6 项、6 项均按时、无容量或图冲突区违规、无未解决持续阻塞、两架次穿越请求都获准；事件满足故障暂停、道路等待及航班依赖。三次输入哈希应相同。未来修改策略可能改变选车、等待量及具体时刻，变化应通过事件解释，而不是强制匹配每个历史数值。

本配置没有随机扰动，种子 1 用于固定运行协议。一次场景中滚动策略等待稍短，不能据此得出统计上的策略优越性。此处没有触发循环死锁，也没有触发节点改道；它们由第 7 节的专门测试覆盖。

## 6. 五个页面的手动操作验收

以下是额外的在线交互验收，不要求复刻离线场景的秒级时序。使用独立数据库和端口，保留原有 `8000/8501` 现场。

终端 A，在仓库根目录启动独立 API：

```bash
source .venv/bin/activate
mkdir -p results/manual-acceptance
APRONOPS_DB_PATH=results/manual-acceptance/operations-001.db \
  python -m uvicorn apronops.api.main:app --host 127.0.0.1 --port 8001
```

终端 B，若第 4 节的 `8502` 看板仍运行，先在那个终端按 Ctrl+C，再启动：

```bash
source .venv/bin/activate
APRONOPS_API_BASE=http://127.0.0.1:8001 \
  python -m streamlit run apronops/dashboard/app.py --server.port 8502
```

打开 <http://127.0.0.1:8502>。重复验收要全新现场时更换数据库文件名，不删除旧库；使用相同文件名表示恢复上次现场。在线默认每 2 秒墙钟推进 5 秒仿真，不应把在线等待时间直接套用到离线时间表。

### A. 运行总览：道路、派单、泊位与调度

1. 勾选“叠加飞机滑行道参照”，再取消，确认车辆路网独立存在。高亮最多 3 辆车，查看轨迹、速度、任务和等待原因。
2. 展开“查看起终点行车路线”，选择 `DEPOT_BAG_W → SP_01`，勾选“在图中显示路线”。应显示车辆道路上的路线、距离和交叉点数量；距离不含排队时间。
3. 创建任务：ID `UI_ACCEPT_BAG_001`，类型 `baggage_tow`，起点 `DEPOT_BAG_W`，终点 `SP_01`，优先级 4，要求完成时间 40 分钟。应出现新任务，车型兼容且可达的空闲车负责执行。再次用相同 ID 创建应显示冲突，任务不重复。
4. 观察车辆前往起点、办理、运输、服务、返程；在基地明细中核对 `已占用 + 进站预留 ≤ 泊位数`。若当前没有排队，使用第 4 节固定回放看满位过程，不能把空队列当作排队测试已经触发。
5. 展开“调度策略”，依次选择并应用三种规则，最后保留“滚动联合优化（每 15 秒）”。刷新后选择保持；原执行任务的车辆归属与阶段保留，新任务使用所选规则。

### B. 航班与穿越：任务生成、延误、空地互锁

1. 创建 `UI_ACCEPT_FLIGHT_001`，机位 `SP_07`，距当前仿真时间到位 10 分钟，到位至离位 45 分钟。应新增一个航班及 3 个关联任务；检查包含行李与配餐依赖。
2. 选择该航班，将到位与离位顺延 5 分钟，提交航班延误。未开始任务的时间窗应更新，航班版本增加。已开始/完成任务保护用第 7 节精确测试验证。
3. 在“录入飞机穿越请求”输入 ID `UI_ACCEPT_CROSS_001`、航空器 `SYN_UI_01`、交叉点 `X_04`、预计开始 30 秒、申请推迟 20 秒、持续 45 秒，保存。
4. 比较预测、申请和实际窗口。只到预测时刻不会直接获得占用权；申请后等待冲突区清空再授予，实际持续 45 秒。恰好没有车辆到达时看不到停车；第 4 节及互锁测试覆盖实际车机相遇。
5. “载入航班与穿越演示”是另一条快捷入口，会添加 1 个合成航班、3 项任务及 2 个请求，重复点击不重复创建。它会增加在线任务数，不把点击后的现场和离线 6 项任务结果比较。

### C. 异常处置：故障、封路、恢复和事件

1. 选择一辆正在执行任务的车，注入“定位质量下降”。确认原任务仍保留，车辆暂停且出现告警；填写“定位恢复验收”，点击“确认恢复并关闭告警”，应从原位置和阶段续跑。
2. 未取货通信故障转派可在第 4 节前两种策略回放查看；在线时机较难把握，可用第 7 节测试精确复核。已经取货时不能期待自动把货物转交另一辆车。
3. 选择双向路段 `R_004 ↔ SP_01`，原因为“验收临时施工”，点击“封闭道路”。回总览看第 A 节路线，应提示暂无可通行路线，地图显示红色虚线。页面其他状态仍可查看。
4. 在异常处置页选择对应道路告警，填写“施工结束验收”，确认恢复。路线重新出现，封路记录保留恢复时刻及说明。检查“近期操作与任务事件”能够解释故障、封路、恢复和任务变化。

### D. 运营复盘：正确读取指标

查看任务完成率、到期任务准时率、告警解决率及逾期未完成。尚无到期任务时应显示“暂无到期任务”，不能显示为已实现 100% 准时。到期但未完成的任务进入准时率分母；关闭告警计入告警解决率，不代表一次人工接管车辆。在线总任务包含种子任务及手动新增任务，结果无需等于离线 6/6。

### E. 实验回放：上传、拖动与隔离

选择或上传第 4 节的 `replay.json`；分别看初始、中间和最终帧，检查任务、车辆、泊位和封路变化。停止本节独立 API 后，回放仍应可读。上传无效 JSON 应显示校验错误。回放最大 100 MB，只读 JSON，不执行其中内容；支持完整自动播放与离线 HTML 下载，下方保留独立滑块用于逐帧核对。

### F. 重启恢复及接口

在任务运输、服务或挪车时停止**独立 API**，再用终端 A 的原命令和同一数据库重启。确认已有任务、所选策略、故障、封路和队列未丢失；车辆不会因重启退回路段起点，停机期间不推进仿真。在线过程持续运动，严谨的阶段/位置对比使用下节快照测试。

接口文档位于 <http://127.0.0.1:8001/docs>。只读查询示例：

```bash
curl --fail http://127.0.0.1:8001/health
curl --fail http://127.0.0.1:8001/state
curl --fail http://127.0.0.1:8001/dispatch/policies
curl --fail 'http://127.0.0.1:8001/events?task_id=UI_ACCEPT_BAG_001'
curl --fail http://127.0.0.1:8001/metrics
```

另外有 `/vehicles`、`/tasks`、`/alerts`、`/tracks`、`/layout`、`/flights`、`/crossings/occupancies` 等读取接口，以及 `/ws/state` 状态推送。看板实时刷新本身使用完整状态快照，不依赖浏览器直连 WebSocket。

## 8. 证据文件与当前边界

每个策略子目录保存：`manifest.json`（代码/输入/环境与运行状态）、`inputs.json`（实际输入）、`layout.json`（地图）、`events.jsonl`（精确事件）、`frames.jsonl`（采样状态）、`tasks.csv`（任务时间）、`summary.json`（最终指标）、`performance.json`（计算耗时）、`replay.json`（便携回放）。批次根目录 `comparison.csv` 用于比较。`status=completed` 只表示跑到观测终点，任务完成与否还要看 `completed_tasks/unfinished_tasks`。

验收留存应包括场景配置、代码提交和整个输出目录；从云服务器下载单个 `replay.json` 即可在本机看板回放，下载整个目录则能复核输入及精确事件。运行协议详见 [实验与回放](experiments.md)。

当前基地泊位与等候区是逻辑资源，没有实体泊位几何或有限等候区长度；循环恢复依赖空闲逃逸泊位及可通行道路；路段中相向阻塞仍可能无法自动解决。滚动策略是有界候选集合上的联合匹配，不保证全局最优。零违规只对应模型内的容量和图冲突区检查。当前也没有多进程共同调度、完整身份权限体系、分布式实验或训练功能。
