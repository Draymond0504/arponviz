# 航班保障与飞机穿越（第二阶段）

本阶段把航班时间窗、保障依赖和飞机穿越纳入同一仿真世界。看板新增“航班与穿越”，仍采用 Layout H 独立车辆道路，未接入真实航班/航空器定位、机场放行系统或 MAPPO 策略。

## 使用

1. 在“航班与穿越”中点击“载入航班与穿越演示”，生成一个合成航班、三个保障任务和两个穿越请求。重复点击不重复生成；正常启动不会自动注入演示。
2. 观察航班保障进度和任务等待原因。到位时间之前任务不分配；行李与配餐完成后才允许保障后检查任务进入调度。
3. 返回运行总览查看车辆。黄色圆形覆盖提示交叉区范围，飞机占用或等待清空时显示管制标记，车辆等待原因显示相关飞机与交叉点。
4. 可自行创建航班、提交延误，以及录入新的穿越请求。所有操作沿用事务持久化和错误回滚。

演示数据在 `apronops/flights.py::load_demo` 定义：机位 SP_20，20 秒后到位，45 分钟后要求离位；X_11/X_10 两处请求相对预测推迟 20 秒。请求不代表该保障航班自身的完整滑行轨迹，只模拟另一架飞机对服务车路网的外部约束。

## 航班与任务

航班运行 ID 唯一，同一航班不同日期应使用不同 ID。创建或更新接口采用固定 ID，不根据次数新增任务。

| 模板任务 | 起点 | 终点 | 服务时长 | 前置依赖 |
|---|---|---|---|---|
| 行李保障 | 按机位东西位置选择行李基地 | 机位服务点 | 480 秒 | 无 |
| 配餐保障 | 配餐基地 | 机位服务点 | 600 秒 | 无 |
| 保障后检查 | 巡检基地 | 机位服务点 | 180 秒 | 行李与配餐完成 |

这是 `turnaround_v1` 合成模板，不代表机场通用作业规程。全部任务在预计到位时间释放，截止时间为预计离位时间；不模拟提前调车。行李与配餐在依赖上可并行，但当前图模型的同一服务点占位规则可能使车辆在进入时串行等待。

任务仍使用 `Task` 模型，通过 `flight_id`、`release_at`、`depends_on` 和 `service_duration_s` 表达服务任务，无需维护两套状态机。业务期限为软约束：迟到继续服务，并计入逾期指标。

- 相同航班及完全相同的计划重复提交是幂等操作。
- 更新须传当前 `expected_revision`，避免覆盖其他操作已修改的计划。
- 延误更新待执行任务的释放时间及截止时间；已分配或执行中的任务保留释放时间和实际进度，只更新截止时间；已完成任务保留原截止时间及结果。
- 尚未执行时 API 可修改机位；已有任务开始、转派或完成后不允许直接换机位。
- 已完成全部保障的航班不接受新的计划变更。航班取消、拆分任务、货物交接和真实 SOP 尚未建模。

## 交叉区和停止线

每个 crossing 节点为一个图上的冲突区中心，区段沿各相邻道路延伸。半径采用 `min(3 m, 最短相邻路段长度 / 3)`，相邻交叉区不会重叠；车辆在进入边距中心该半径处等待。地图圆形仅示意这一范围。

实际 Layout H 的部分节点很近，因此该半径可能小于真实车辆尺寸。这里验证的是点车辆和图冲突区的通行约束，不是对机翼/车身包络、机场实际净空或停止线距离的校核。

交叉区一次只允许一辆车占用。该车越过出区边界后才释放许可，区内车辆拥有先清空的优先级，防止旧的按车辆 ID 让行规则阻止清空。普通道路依然是双向单中心线抽象，未实现车道级会车。

飞机穿越分四种状态：

| 状态 | 含义 |
|---|---|
| `scheduled` | 已录入请求，但尚未到申请时间 |
| `waiting_clearance` | 申请已到，等待区内车辆或前一架飞机清空 |
| `active` | 已授予飞机占用，禁止车辆进入 |
| `completed` | 授予的占用时段结束 |

`predicted_start/end` 是预测窗口：默认在线策略按距离寻路；第三阶段 `deadline_forecast` 实验策略使用已公布的预测窗口规划路径，但预测本身不作为禁行依据。`requested_start/end` 是外部模拟的申请时段；获准后填充 `actual_start/end`，并保留请求的完整持续时间。这里的 actual 是仿真实际授予时间，不是从真实定位设备接收的占用事实。

请求到达时即禁止新车辆入区。已经在区内的车辆允许继续离开；区内故障车不被瞬移、删除或强制清空，飞机请求持续等待。多个飞机请求按申请时间和 ID 排队，不能同时获准。

因此这是可延迟飞机进入的**仿真互锁机制**。真实机场中对航空器的放行权及非受控闯入不在本版本能力范围；不能把该机制宣称为已验证的真实空地安全系统。它也区别于“固定且不可延迟的飞机占用时间表”，后者需要额外的预约、鲁棒时间裕度及侵入处置模型。

原来的“进入交叉节点后停 3 秒”已取消。无占用时正常通过；有占用时在区外停车。积分跨越停止线时执行位置截断，防止数值步长造成越线；不等同于真实制动器的连续可行轨迹。

## 时间与推进

外层 `tick` 仍默认推进 5 秒，但所有车辆按同一个最多 0.5 秒的子步时钟推进，并在申请时刻、授予结束时刻、任务释放时刻进一步分段。短于外层 tick 的占用窗口不会被整步跳过。

外部接口输入必须包含时区，例如 `2026-10-30T10:00:00+08:00` 或 `2026-10-30T02:00:00Z`。内部仍保持已有 UTC 无时区 datetime 存储口径；返回的无时区时间一律解释为 UTC。看板窗口表展示北京时间，原始任务表时间为 UTC。

不能向过去插入占用请求，也不能更改已有请求 ID 对应的时间或位置；本阶段尚未提供占用取消/延长接口。录入时应留出足够提前量。请求与航班相互独立，更新航班不会偷偷移动已有穿越请求。

## 数据与恢复

当前快照为版本 3，新增随机源、事件计数、策略名及行驶里程；保留版本 2 的航班、任务依赖及服务时长、预测/申请/授予窗口、交叉区车辆许可。版本 1 快照可自动读取：保留车辆、任务、封路和时间，新增集合为空，并取消旧固定 3 秒等待。版本 2 快照也可兼容读取；首次成功推进/操作后写入版本 3。

数据库名仍为 `apronops-operations-v1.db`，不会因升级而清空现场。`TaskORM` 继续作为指标投影，新增任务上下文、Flight 与 CrossingOccupancy 的权威恢复来源是事务内的完整快照。升级后不要使用旧程序直接打开已写入版本 3 的数据库；可使用升级前备份。

## 接口

| 接口 | 用途 |
|---|---|
| `GET /flights` | 航班计划、版本、保障进度 |
| `POST /flights` | 创建或修订 `{id, stand_id, arrival_at, departure_at, expected_revision?}` |
| `GET /crossings/occupancies` | 全部预测、申请和授予窗口 |
| `POST /crossings/occupancies` | `{id, crossing_id, aircraft_id, predicted_start, predicted_end, requested_start, requested_end}` |
| `POST /scenarios/turnaround-demo` | 一次性载入合成场景，多次请求不重复生成 |
| `GET /state` | 新增 flights、occupancies、crossings，以及任务等待原因 |

交叉节点不允许作为手动任务的停靠起终点，避免将服务作业永久安排在冲突区内。其他接口、故障恢复及封路规则继续有效。

## 验证与后续

测试包含重复提交、版本冲突、延误与已执行任务保护、任务依赖全链路、预测与申请分离、区外停车、短窗口捕获、空地互斥、区内故障、相向车清空、重启恢复和看板表单操作。

第三阶段已完成无界面实验核心、配对种子比较、预测等待规则和看板回放，见 [实验与回放](experiments.md)。默认在线最短路仍按距离，尚未完成训练/测试划分、滚动优化算法或 MAPPO 接入。
